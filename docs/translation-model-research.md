# 本地翻译模型选型调研

> 调研时间：2026-10-22。目标：给 smartpaste 加一个本地大模型翻译工具，离线、无 API Key。
> 所有体积按 Q4_K_M GGUF 估算；厂商自评数据都标了来源，社区横评互相矛盾的地方单独说明。

---

## 0. 先说结论

| 结论 | 内容 |
| --- | --- |
| 默认模型 | **HY-MT1.5-1.8B**（腾讯混元，官方 GGUF，Q4_K_M 约 1.1 GB）。中文↔外文是同尺寸最强的一档，1.8B 的体量对截图工具最合适 |
| 备选（许可证更干净） | **TranslateGemma-4B** 或 **Qwen3.5-4B**。前者是 Google 的翻译专用模型（保留视觉），后者 Apache-2.0、无地域限制 |
| 不建议 | 7B 以上当默认（冷启动 3–10s、常驻 5 GB，截图工具用不上）；NLLB（CC-BY-NC，禁商用）；小尺寸 VLM 端到端出图（拿不到 bbox，密集文本会漏字） |
| 必须先定的 | 翻译的输入是**纯文本**还是**截图区域**。前者只需 MT 模型；后者还得先解决 OCR，选型完全不同 |

一句话理由：翻译是"窄任务"，专用小模型的性价比远高于通用大模型。2026 年这个赛道的第一梯队已经是 1–4B 的专用 MT 模型，7B 通用模型在翻译上打不过它们。

## 2. 质量数据：别全信，但得知道大概

**厂商自评（都是自家 benchmark，横比要打折）**

- HY-MT1.5-1.8B：FLORES-200 约 78 分，官方称达到 Gemini-3.0-Pro 的 90 分位；50 token 平均 0.18 s。1.5 版相对 1.0 版主要修了"译文夹注释、语种混杂"。
- Hunyuan-MT-7B（1.5 的前代）：WMT25 参赛 31 个语向拿 30 个第一，英→简中人工评分 87.2。
- TranslateGemma：WMT24++ 上 MetricX（越低越好）4B=5.32、12B=3.60、27B=3.09，12B 打赢 Gemma 3 27B 基线。

**社区横评（矛盾，正是要自己跑的理由）**

- 一份 ≤7B 的 12 模型横评：TranslateGemma-4B 综合第一（90.0）> Qwen3.5-4B（88.0）> Gemma3-4B，而 HY-MT1.5-1.8B 只排第 7，**可靠性一项只有 0.3**——大概率是没按官方模板喂 prompt，或者踩了小模型的重复/漏译。
- 另一份个人电脑环境的横评：HY-MT1.5-1.8B 的 BLEU/chrF 全场最高（36.87 / 67.14），LLM 打分 8.67。

两份结论相反，说明**这类评测对 prompt 格式、采样参数、文本类型的敏感度极高**。所以第 5 节给了自测方案，别跳过。

**踩坑记录（社区反馈 + llama.cpp 通用经验）**

- HY-MT 系列**必须用官方 prompt 模板**，用 "translate this: xxx" 这种野路子质量会掉一档。模板见官方 README，中→外要求用中文指令 + 全称语言名。
- 小模型长文本偶发漏句/复读：`--repeat-penalty 1.1`、`top_k 20 / top_p 0.6 / temp 0.7`（官方推荐值），长文按句切分再译。
- HY-MT1.5 的 **1.25-bit 440MB 版本暂时不能用**：它依赖腾讯自研的 STQ 量化 kernel，llama.cpp 的 PR #22836 至今未合入（已核实 `merged: false`）。想要 440MB 得自己打补丁或走腾讯的 AngelSlim 工具链。

## 3. 关键取舍：这个工具的输入到底是什么

截图工具没有 OCR（README「已知限制」里写着）。所以"翻译"有两种形态，选型完全不同：

**形态 A：文本进、文本出（推荐 v1）**
选区 → OCR 出文字 → MT 翻译 → 弹面板显示 / 复制到剪贴板。
MT 模型只需处理纯文本，选型自由，延迟可控，出错好定位。

**形态 B：图进、图出（原位覆盖译文）**
需要 OCR 的 **bbox + 行合并**，再做排版回填。MT 模型给不了 bbox，必须配检测模型。工作量大 3 倍以上，v1 不建议。

**OCR 三条路**

| 方案 | 体积 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Windows.Media.Ocr（系统自带） | 0 | 零依赖、零分发成本 | 需装语言包；从 Rust 走 WinRT 要给 `windows` crate 开 `Media_Ocr` feature，纯 windows-sys 用不了；精度对 UI 文本一般 |
| RapidOCR / PaddleOCR-ONNX | ~15–20 MB 模型 + onnxruntime | 中英日精度最好，直接给 bbox，能排版 | 多一个 ORT 依赖（DLL 十几 MB） |
| VLM 端到端（Qwen3.5-4B / TranslateGemma-4B） | 2.3–2.4 GB | 一个模型搞定，省掉 OCR 链路 | 密集文本漏字、无 bbox、慢（一张截图 2–5 s），不适合做交互功能 |

结论：走形态 A + RapidOCR（想要 bbox 和精度）或 Windows OCR（想要极简）；VLM 端到端留作以后的"整图翻译"实验。

## 4. 部署形态：怎么塞进一个单 exe 的 Win32 程序

现在项目是"单 exe、无运行时依赖、`opt-level="z"`"。接 1 GB 模型必然要打破其中几条，三种做法：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 进程内链接 llama.cpp** | `llama-cpp-2` / `llama-cpp-sys-2` crate，静态编 C++ | 真·单文件，无 IPC | 构建要 cmake + MSVC，增量编译慢；`panic="abort"` 下一旦推理崩溃整个程序跟着挂；二进制涨 10–20 MB |
| **B. sidecar `llama-server.exe`** | 首次翻译时 spawn，`127.0.0.1:<port>` 上 OpenAI 兼容接口 | 崩溃隔离、易升级、开发调试简单（curl 就能试） | 多 30–50 MB 的 exe+DLL；要管端口、生命周期、孤儿进程 |
| **C. 复用用户已装的 Ollama / LM Studio** | 直连 `localhost:11434` | 零分发成本、模型管理交给别人 | 用户得先装 Ollama；不适合当默认路径 |

**建议：B 为主，C 作为高级选项（配置里填 base_url 就切过去），A 不做。**
理由：这个项目最怕的是"为了一个可选功能把构建链搞脏"。sidecar 让翻译模块变成一个可以整个删掉的子系统，也方便以后换模型不用重编。

**模型分发**：不要打包进 exe。首次使用时从 ModelScope/HF 下载到 `%APPDATA%\smartpaste\models\`，带 SHA256 校验和断点续传。这同时绕开了许可证问题——**权重由用户自行下载，程序本身不 redistribution**，混元协议里"EU/UK/韩 不适用"那条就不会烧到你的 MIT 发布上。

**常驻策略**：截图工具大部分时间不翻译。冷启动 1.8B Q4 约 2–5 s（mmap），建议"首次翻译时拉起 → 空闲 5 分钟杀掉"，或者干脆按需起进程 + `--no-mmap` 预热。

**线程与参数**：`-t` 取物理核数的一半左右（超线程对解码帮助不大），`-c 2048`（UI 文本用不上长上下文），`--repeat-penalty 1.1`，`-ngl 0` 纯 CPU，检测到独显再 `-ngl 99`。

## 5. 自测方案（选型最后一步，别省）

拿 60–100 条**真实截图文本**做 A/B，比任何榜单都准：

1. 样本分层：英文 UI 短句 30 条、中文→英文 20 条、技术术语/代码标识符混排 20 条、长段落 10 条。
2. 候选：HY-MT1.5-1.8B(Q4/Q8)、TranslateGemma-4B、Qwen3.5-4B。全部走官方 prompt 模板，采样参数固定。
3. 评分维度（人工 0–4 分 + 机器指标辅助）：
   - 准确性：有没有漏译、错译、加解释
   - 不该翻的有没有翻：`Ctrl+Shift+A`、`config.txt`、`PNG` 这类必须原样保留
   - 格式：换行、列表、标点是否保持
   - 语言泄漏：译文里混没混原文
   - 延迟：单条 + 10 条批量
4. 通过线：中英双向平均 ≥3.2 且"不该翻的"错误率 <5%。

顺带记录内存峰值和首次加载时间，写进 README 的「已知限制」。

## 6. 附：官方 prompt 模板（直接抄）

中↔外：
```
将以下文本翻译为{目标语言全称}，注意只需要输出翻译后的结果，不要额外解释：

{原文}
```

外↔外（不含中文）：
```
Translate the following segment into {target_language}, without additional explanation.

{source_text}
```

术语干预（截图场景很实用，可以给一套内置术语表：UI 控件名、常见缩写）：
```
参考下面的翻译：
{原文术语} 翻译成 {目标术语}

将以下文本翻译为{目标语言全称}，注意只需要输出翻译后的结果，不要额外解释：
{原文}
```

推理参数（官方推荐）：`top_k=20, top_p=0.6, repetition_penalty=1.05, temperature=0.7`。
