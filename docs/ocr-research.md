# OCR 选型调研（截图翻译前置）

> 调研时间：2026-10-22。承接 `translation-model-research.md`。目标：给 smartpaste 的翻译工具找一条"截图 → 文字 + 坐标"的路径。

---

## 0. 结论

| 结论 | 内容 |
| --- | --- |
| v1 默认 | **PP-OCRv5/v6（ONNX，20–80 MB）**。CPU 几百毫秒、逐行给 bbox 和置信度、Apache-2.0、不产生幻觉。截图里的 UI 文字本来就是它最擅长的场景 |
| 想要"大模型 OCR" | **PaddleOCR-VL-1.6（0.9B，Apache-2.0，官方 GGUF，llama.cpp 已合入）**。文档截图（论文/表格/公式）质量明显高一档 |
| 最对口截图场景 | **HunyuanOCR-1.5（1B，腾讯）**。官方基准里明确有"截屏"场景，且能一次前向同时出检测框和译文；但许可证有地域限制、CPU 上慢，适合当"高精度模式" |
| 一句话 | 轻量检测识别做默认，VLM OCR 做可选。别把 VLM OCR 当默认路径——它慢、且会"猜"字 |

**先纠正一个预期**：OmniDocBench 是**文档解析**榜（版面、表格、公式、阅读顺序），跟"截图里的 UI 文字"是两回事。榜单第一名在 12px 的按钮文字上未必比 20 MB 的 PP-OCR 强，因为后者训练数据里全是这类干净短文本。截图场景的难点在别处：小字号、ClearType 子像素彩边、深色底、图标混排、代码字体。

## 1. 三类方案

### 1.1 轻量检测 + 识别（传统流水线）

| 模型 | 体积 | 语言 | 许可证 | 特点 |
| --- | --- | --- | --- | --- |
| PP-OCRv6 tiny/small/medium | 4.4 / 20.4 / 73 MB | 50（medium） | Apache-2.0 | 字准确率 73.5 / 81.3 / 83.2%（自家内部集） |
| PP-OCRv5 mobile / server | 16 / 81 MB | 100+ | Apache-2.0 | 上一代，社区工具链最全，RapidOCR 就是打包它 |
| Surya 650M | ~1.3 GB | 90+ | Apache-2.0（代码）/ OpenRAIL-M（权重） | 版面+表格强，比 PP-OCR 重很多 |

优点：**快**（一张 1080p 截图 det+rec 约 0.2–0.6 s，纯 CPU）、**每行有 bbox 和 score**、**不会编造文字**。
缺点：不做版面语义（多栏、表格结构、阅读顺序），竖排和艺术字弱。

### 1.2 端到端 OCR 专用 VLM（2026 的主流答案）

| 模型 | 参数 | 最小部署 | 许可证 | OmniDocBench | 备注 |
| --- | --- | --- | --- | --- | --- |
| **PaddleOCR-VL-1.6** | 0.9B | 主模型 GGUF ~0.3–0.9 GB + mmproj ~0.88 GB | **Apache-2.0** | v1.6 约 96.3（自评） | 111 语种；1.5 起支持 text spotting（逐行框 + 多边形）；官方 GGUF，llama.cpp 自 b8110 起合入；**本质是级联**（版面检测 + 分块 VL 识别） |
| **HunyuanOCR-1.5** | 1B | 需自行转 GGUF（官方只发 safetensors） | 混元社区协议（EU/UK/韩排除，1 亿 MAU 门槛） | v1.6 端到端 94.74 | 纯端到端单次前向，12 种任务；DFlash 投机解码已并入 llama.cpp（b11103+）；自建 9 场景基准**含"截屏"**；能直接做"图 → 译文" |
| GLM-OCR | 0.9B | ~1.4 GB | MIT | 95.22 | 表格/公式强，语种少 |
| dots.ocr | 1.7B | ~3.2 GB | MIT | 90.8 | 强在 grounding，100+ 语种 |
| DeepSeek-OCR-2 | 3B-A0.5B | ~2.5 GB | MIT / Apache | ~87–91 | 吞吐怪物（A100 上 200k 页/天），精度让位 |
| olmOCR 2 | 7.7B | ~16.6 GB | Apache-2.0 | 81.8 | 英文 PDF 批量，桌面场景太重 |

优点：版面理解、表格、公式、阅读顺序一次搞定；HunyuanOCR 甚至能直接输出译文。
缺点：**慢**（CPU 上一张密集截图 5–30 s 量级，需实测）、**会幻觉**、依赖重。

### 1.3 通用 VLM 顺带做 OCR

Qwen3.5-4B / Qwen3-VL-8B 这类也能读图，但按 OmniDocBench 全线输给 0.9B 专用模型。唯一好处是"一个模型既能 OCR 又能翻译还能问答"。不建议为此牺牲精度和延迟。

## 2. 四个必须知道的坑

**① 幻觉比漏字更致命。**
VLM OCR 会按语言先验"补全"看不清的字。腾讯自己开了 CHAOS-Bench 专门测这个（把字改成无意义扰动，看模型会不会照实输出），HunyuanOCR-1.5 拿到页均召回 14.15——这已经是"最优"，说明**忠实还原仍是开放问题**。
对翻译工具来说，把模糊的字猜成通顺句子 = 译错原文，用户还看不出来。传统 OCR 每条给 confidence，低于阈值可以标"识别存疑"，这条降级路径必须有。

**② "端到端"和"级联"是两种东西，别混着比。**
PaddleOCR-VL 在生产里是**流水线**：版面检测模型先切块，再逐块喂 VLM 识别。所以你拿到的 bbox 来自检测模型，不是 VLM。想自己复刻，就得同时跑检测模型 + 维护分块逻辑。
HunyuanOCR 是真正的单次前向，接口简单，但代价是长输出解码慢（所以才有 DFlash）。

**③ 指标不可比。**
PP-OCRv6 medium 的 83.2% 是**字符准确率**，OmniDocBench 的 96.3 是**文档解析综合分**。两个数字放一张表里排名是耍流氓。同理，厂商自评、不同 benchmark 版本（v1.5 / v1.6）、不同语言的覆盖率，都不能直接横比。

**④ 许可证比模型更容易翻车。**
- PaddleOCR-VL / PP-OCR：Apache-2.0，最省心。
- HunyuanOCR：混元社区协议，**不含 EU/UK/韩**，1 亿 MAU 以上要单独授权，禁止用输出去训练别的模型。—— 对 MIT 项目发布程序没问题（权重让用户自己下），但别把权重打进安装包。
- MinerU 在 checkpoint 之间换过协议（2.5 是 AGPL-3.0，2.5-Pro 改 Apache-2.0），挑模型时认准具体 checkpoint。

## 3. 在 smartpaste 里的三条落地路径

| 路径 | 做法 | 体积 | 延迟（估） | 风险 |
| --- | --- | --- | --- | --- |
| **A. ONNX + PP-OCR**（推荐默认） | Rust 用 `ort` crate 加载 PP-OCRv5 det/rec/cls，输入选区 DIB | +20–80 MB 模型 + onnxruntime DLL ~30 MB | 0.2–0.6 s | 无 |
| **B. llama.cpp + PaddleOCR-VL**（可选档） | 复用翻译要起的 `llama-server`，加 `--mmproj` | +1.2 GB 模型，server 侧复用 | CPU 5–30 s / GPU 1–3 s | 需实测截图小字效果 |
| **C. Windows.Media.Ocr**（极简） | `windows` crate 开 `Media_Ocr`，走 WinRT | 0 | 0.1–0.3 s | 要语言包；中文精度一般；和现有 windows-sys 体系割裂 |

路径 A 的具体选型：PP-OCRv5 mobile（16 MB，够用）或 v6 medium（73 MB，字准确率 +2pt）。两者都是 det（DBNet）+ rec（SVTR/CTC）两个模型，输出四边形 + 文本 + 置信度。

**和翻译模块的衔接**：
1. OCR 出 `Vec<Line { text, quad, score }>`
2. 按行聚类成 block（同 y 邻近、间距阈值），过滤 score < 0.5
3. 过一道"该不该翻"的规则：纯 ASCII 标识符 / 快捷键 / 路径 / 单词长度 < 2 → 跳过
4. block 批量送 MT，保留 block 索引，回来按索引回填
5. 缓存：同一张图 + 同一目标语言 → 命中缓存

第 3 步那个过滤器，比选哪个 OCR 模型更影响体验。截图里一半的"文字"是不该翻的。

## 4. 升级路径

- **什么时候才值得上 VLM OCR**：用户截的是论文、表格、发票、扫描件，且明确切到"文档模式"。这时候 PP-OCR 会因为多栏和表格结构直接崩掉，而 0.9–1B 的 VLM 恰好是为此训练的。
- **先上 PaddleOCR-VL 还是 HunyuanOCR**：
  - 优先 PaddleOCR-VL：Apache-2.0、官方 GGUF、llama.cpp 主线支持、111 语种，工程风险最低。
  - 只有当"截屏小字"实测明显更好时才换 HunyuanOCR——它的 9 场景基准里有"截屏"，这是唯一对口的公开证据，但需要自己转 GGUF，且许可证收窄。
- **不建议**用 OCR VLM 一步出译文（HunyuanOCR 支持）：译文质量不如专用 MT，且无法按块重译、无法缓存、无法让用户改术语。分成两步，每步都能单独换。

## 4.5 决策记录：为什么不用 HunyuanOCR-1.5 一步出译文

HunyuanOCR-1.5 确实支持"图 → 译文"单次前向（拍照翻译任务，ICDAR 2025 DIMT 小模型赛道冠军）。评估结论是**不作为默认路径**，四条理由按权重排序：

**① 文本 MT 模型无论如何都得装。**
这个工具除了截选区，还要翻剪贴板文本、用户手输的句子、以及"只重译某一块"。HunyuanOCR 只吃图，这些场景一个都覆盖不了。既然 HY-MT1.5 已经常驻，OCR 出来的文字再走一遍专用 MT 的边际成本≈0，质量还更高——那"省一个模型"的收益根本不存在，实际是**多**常驻一个 1.5–2 GB 的模型（1B 权重 + SigLIP-400M 视觉塔）。

**② 训练目标不一样。**
OCR 模型的主目标是"忠实还原文字与版式"，翻译是附属能力（14 种小语种→中/英）。HY-MT 的主目标就是译文质量，还叠了翻译域的在线蒸馏 + 细粒度翻译奖励 RL。中英互译这种主战场，专用 MT 的赢面明显更大。

**③ 单次前向丢掉了所有可控性。**
- 改一个 OCR 错字后重译 → 必须重跑整张图
- 换目标语言 → 重新做视觉编码（贵的那一半）
- 术语表 / 上下文 / 格式保留 → HY-MT 原生支持，端到端出不来
- 按块缓存 → 没有中间表示就没法缓存
视觉编码是这条链路里最贵的一步，端到端等于每次都要重付一次。

**④ 失败面不可分。**
译错了，你分不清是 OCR 认错还是翻译翻错。两段式有中间产物，可以直接给用户看"我认到的是这段"，出错能定位。

**许可证不构成理由**：HunyuanOCR 和 HY-MT1.5 同属混元社区协议，地域排除与 MAU 门槛完全一样，选谁都不改变这件事。

**什么情况下反过来选端到端**：整图/拍照/文档场景，**视觉上下文本身就是翻译质量的一部分**——表单里 "Name" 和 "张伟" 分属两个框、表格列头决定单元格语义、代词指代靠版面判断。这类图给专用 MT 一串打散的文本反而更差。所以正确形态是：**文档模式才端到端，UI 文字模式走两段式**。

**推荐的折中**：HunyuanOCR 只做 OCR 那半——出 bbox + 文本，再喂 HY-MT。这样既白拿了视觉版面理解，又保留了全部可控性。代价是多一次推理，但只在"文档模式"下发生。

## 4.6 如果需求收窄为「只翻当前选区」

收窄之后，4.5 的第 ① 条（还得养一个文本 MT）直接失效——不再有剪贴板文本、手输句子、单块重译这些场景。剩下的判断变成**三个功能边界**，而不是架构优劣：

**① 翻译方向是单向的。**
HunyuanOCR 的翻译任务只覆盖「14 种小语种 → 中/英」+「中英互译」，官方明确列的方向不含 中→日、中→法、法→德 这类。截一张中文界面想翻成日文，它做不了。HY-MT1.5 是 33 语种 + 5 民汉、1056 个方向全互译。
→ 如果产品定位就是中英互译，这条不成立；只要想支持"中→任意"，它直接出局。

**② 拿不到原文/译文对齐。**
翻译任务输出的是译文，带框的是另一个任务（text spotting）。两个都要 = 两次前向，比两段式更慢。而"翻译截图"的产品形态，多半需要至少能看一眼"它认到的原文"，否则译错了用户完全无从发现。
→ 如果 UI 就是"弹窗显示译文 + 复制"，这条不成立。

**③ 幻觉没有中间产物兜底。**
UI 小字 + ClearType 彩边是最容易触发"猜字"的输入。端到端方案里，猜错的字直接进译文，没有任何地方能暴露出来。两段式至少能把 OCR 结果摆给用户看。

**质量预期要摆正**：官方口径是 Other2Zh 73.62 / DoTA en2zh 83.48，对比 Qwen3-VL-235B 的 77.20 / 80.01——**不是"对标 235B"，是各赢一项、整体略低**。跟专用 MT 比，中英互译大概率再低一点。

**结论**：
- 若 = 中英互译 + 只出译文 + 可接受秒级等待 → **HunyuanOCR 是当前最简方案**，一个模型一次前向，连对齐逻辑都省了。
- 若 = 任意语种 / 要对照 / 要秒出 → 回到「PP-OCR + HY-MT」两段式。

这不是模型选型问题，是**产品定义问题**。三个问题定了，结论自然出来：目标语种范围、输出形态、可接受延迟。

## 4.7 硬件要求（HunyuanOCR-1B）

### 静态占用

| 项 | 体积 |
| --- | --- |
| 语言模型 Q8_0 / Q4_K_M | ~1.1 GB / ~0.7 GB |
| mmproj（SigLIP-v2-400M 视觉塔，一般保持 f16） | ~0.8 GB |
| DFlash 草稿模型（可选，仅提速） | ~0.2 GB |
| llama-server.exe + 后端 DLL | CPU ~40 MB / Vulkan ~50 MB / **CUDA 600 MB+** |
| **合计** | **1.6–2.2 GB**（不含 CUDA 运行时） |

运行内存/显存：权重 2 GB 左右 + KV + 图像激活。社区口径是 llama.cpp 路径 **4 GB 显存或 8 GB 内存**可跑，**16 GB 显存**才叫顺畅；vLLM 路径要 24 GB 起。注意显存不是唯一变量——**mmproj 一旦落到 CPU，整条链路就被它拖住**（已知案例：Qwen3-VL-4B 在 APU 上因为视觉编码器走 CPU，单张 4K 图 40 s）。

### 速度量级（估算，必须实测）

真正的瓶颈是**视觉编码 + 图像 token 的 prefill**，不是文字解码。

| 硬件 | 单张选区（约 600×400） | 说明 |
| --- | --- | --- |
| 桌面 CPU（8 线程） | 3–10 s | 视觉编码就占 0.5–1.5 s |
| 核显（Iris Xe / Radeon 集成） | 3–8 s | 视 mmproj 能否上 GPU |
| 入门独显 4–6 GB | 1.5–4 s | |
| RTX 3060/4060 8 GB | 1–2.5 s | 舒适区 |

校准参考：一台 UHD 630 核显的机器上跑 1B 级 VLM，llama.cpp 纯 CPU 约 14 s/张，OpenVINO + iGPU 中位数约 4 s。

**对 we 这个场景有利的一点**：官方 benchmark 用整页文档，而我们只送选区，通常 400×300 量级。图像 token 数与像素成正比，小图的视觉开销可能只有整页的 1/5–1/10。所以真实延迟大概率比"整页 OCR"的公开数据好看。

### 分发约束（这个项目特有）

现在 exe 只有 2 MB，`opt-level="z"`。如果要带 GPU 后端：

- **CUDA 版**要附带 cudart/cublas，600 MB–1 GB，不可接受。
- **Vulkan 版** ~50 MB，N 卡 / A 卡 / Intel 核显通吃，本地小工具的最优解。
- **CPU 版** ~40 MB，兜底。

建议：Vulkan + CPU 两套后端，启动时探测；不碰 CUDA。另外必须"空闲即卸载"，否则托盘常驻 2 GB 内存，跟这个项目的性格相反。

## 5. 自测方案

固定 20 张真实截图（不是文档），覆盖：浅色 UI、深色 UI、中文小字、中英混排、代码编辑器、PDF、表格、低对比度。

测三件事：
1. **字符准确率**：人工对比原文，统计错字/漏字/多字。
2. **幻觉**：故意截一张含模糊小字的图，看模型有没有"编"出通顺但不存在的词。这是区分传统 OCR 和 VLM 的关键指标。
3. **bbox 质量**：框是否贴行、有没有把两行并成一行、阅读顺序对不对。

通过线：默认路径字符准确率 ≥ 97%，幻觉 0 例；VLM 路径在文档类截图上 ≥ 98%。
